#### **介绍项目：**

> Chat BI 项目
>
> 这是一个面向 VPMS 项目管理数据的“对话式 BI”系统：用户用自然语言提问，系统借助大模型理解需求、生成并执行 SQL，再以表格或图表展示查询结果。
>
> 主要功能包括：
>
> - 支持项目概览、项目阶段、报工/Claim、登录登出等业务模块。
> - 采用“意图识别 → 信息完整性检查 → 追问澄清 → 推荐数据表 → 生成 SQL → 执行查询”的六阶段流程。
> - 支持流式回复、多轮上下文、会话搜索、置顶、重命名和历史记录。
> - 查询结果可生成摘要、解释 SQL、导出 CSV，并绘制柱状图、折线图、饼图、堆积图、组合图等。
> - 带有 JWT 鉴权、行列级数据权限、SQL 限制、请求限流和查询日志等机制。
> - 可切换 OpenAI、通义千问、DeepSeek、Anthropic、OpenRouter 和 AWS Bedrock 等模型服务。
>
> 技术架构：
>
> - 后端：FastAPI、SQLAlchemy、LangChain、MySQL。
> - 前端：Vue 3、Vite、Axios、ECharts、Marked、KaTeX。

> Voltage VPMS Chat BI 是一套面向 VPMS 项目管理业务的智能对话式数据分析系统。它将大语言模型、企业业务规则和数据库查询能力结合起来，让用户无需掌握 SQL，即可通过自然语言完成项目数据查询、统计分析和可视化展示。
>
> 用户可以直接提出类似“本月各项目阶段完成情况如何”“哪些项目存在延期风险”“各团队的报工情况怎么样”等业务问题。系统会自动识别用户意图和所属业务模块，判断查询条件是否完整；当信息不足时主动追问，在条件明确后选择相关数据表、生成 SQL、执行查询，并以文字、表格或图表形式返回结果。
>
> 系统目前覆盖项目概览、项目阶段、Claim/报工、用户登录登出等业务场景。不同模块拥有独立的配置、字段映射、查询要求和业务规则，便于后续继续扩展新的 BI 分析领域。
>
> 完整的智能查询链路包括：
>
> 1. 识别用户意图和业务模块。
> 2. 检查查询信息是否充分。
> 3. 对缺失条件进行交互式澄清。
> 4. 根据业务语义推荐数据表。
> 5. 结合表结构、字段枚举和业务规则生成 SQL。
> 6. 校验并执行 SQL，将结果流式返回前端。
>
> 在结果呈现方面，系统不仅可以展示查询数据，还支持结果摘要、查询来源解释、CSV 导出以及柱状图、折线图、饼图、散点图、堆积图和组合图等多种可视化方式。用户可以自主选择展示字段和图表坐标，并将图表导出为图片。
>
> 项目采用前后端分离架构：
>
> - 后端使用 FastAPI、SQLAlchemy 和 LangChain，负责鉴权、会话管理、意图识别、SQL生成、数据库访问及流式响应。
> - 前端使用 Vue 3、Vite 和 ECharts，提供类聊天式交互、数据表格和可视化分析界面。
> - 数据层支持将系统业务数据与 AI 会话、SQL 日志等管理数据分开配置，并可使用独立的只读查询账号。
> - 模型层支持 OpenAI、通义千问、DeepSeek、Anthropic、OpenRouter 和 AWS Bedrock，能够根据部署环境灵活切换。
>
> 此外，系统还具备多轮上下文、历史会话检索、会话置顶与重命名、SQL执行重试、查询结果反馈、JWT鉴权、请求限流、行列级权限控制以及查询数量限制等能力，具备从内部原型向企业级智能 BI 工具演进的基础。
>
> **项目亮点**
>
> **1. 自然语言直达业务数据**
>
> 传统 BI 往往需要用户理解指标口径、数据表结构或报表操作方式。该项目将这些复杂性封装在对话流程中，让业务人员能够以自然语言直接查询数据库，降低数据分析门槛。
>
> 2. **六阶段智能 Text-to-SQL 流程**
>
> 项目并非让大模型一次性生成 SQL，而是将任务拆分为意图识别、充分性检查、澄清、选表、SQL生成和执行六个阶段。分阶段处理使问题更容易定位，也有利于提高复杂业务查询的准确率和稳定性。
>
> **3. 主动澄清模糊需求**
>
> 当用户未说明时间范围、项目范围、团队类型或统计口径时，系统能够识别缺失信息并提出针对性问题，还可以提供候选选项。这能减少“SQL语法正确，但查询含义错误”的情况。
>
> **4. 业务规则与提示词模块化**
>
> 项目将不同业务领域的配置和规则拆分为独立模块，例如：
>
> - 项目概览
> - 项目阶段
> - Claim/报工
> - 登录登出
>
> 每个模块可分别维护表结构提示、字段映射、示例和业务约束。新增业务场景时，可以沿用现有框架扩展，而不必重写整个对话流程。
>
> **5. 面向企业场景的数据权限控制**
>
> 系统在生成 SQL 后还会结合用户身份应用行级和列级权限规则，使不同角色只能访问授权范围内的数据。这比仅依靠前端隐藏字段更加可靠，也更符合企业内部 BI 系统的数据安全要求。
>
> **6. SQL安全与稳定性保障**
>
> 项目对模型生成的 SQL 设置了多层约束，包括业务规则校验、默认返回数量、最大结果限制和执行失败重试等。同时支持单独配置查询数据库及只读账号，降低生成式 SQL 对业务数据库造成风险的可能性。
>
> **7. 查询过程流式可见**
>
> 后端采用流式接口，前端能够逐步展示分析过程、澄清信息和最终结果。用户不必等待整个链路完成后才看到响应，尤其适合涉及多次模型调用和数据库查询的复杂分析任务。
>
> **8. 从查询到可视化的一体化体验**
>
> 查询结果可以直接转换为多种 ECharts 图表，并支持字段选择、坐标配置、组合序列和图片下载。用户可以在同一个对话页面中完成“提问—查数—分析—制图—导出”的完整工作流。
>
> **9. 结果摘要与可解释性**
>
> 系统能够基于查询结果生成业务摘要，也可以解释查询使用了哪些条件和数据来源。这不仅帮助用户理解结果，也便于核对统计口径，提升 AI 查询结果的可信度。
>
> 10. **多模型适配能力**
>
> 模型服务通过统一接口封装，可适配多种国内外大模型及兼容 OpenAI 协议的服务。企业可以根据成本、网络环境、数据合规性和模型效果选择部署方案，减少对单一供应商的依赖。
>
> 11. **完整的会话化分析能力**
>
> 系统支持多轮追问和上下文继承，例如用户完成一次查询后，可以继续提出“只看华东区域”“再按月份汇总”等增量问题。同时提供历史会话搜索、置顶、重命名和删除，方便用户沉淀和复用分析过程。
>
> 12. **良好的可扩展基础**
>
> 前端、API、对话编排、模型供应商、业务模块和数据库访问层职责相对清晰。后续可以继续扩展新的业务模块、分析指标、图表形式、模型服务或权限策略，而不需要大规模改变现有架构。

### Q1：请介绍一下你设计的 Agent 系统整体架构，为什么选择 LangGraph 而不是纯 LangChain？

**参考回答：**

> 我们的 Agent 系统采用 **"感知 → 规划 → 行动 → 反思"** 的闭环架构。核心用 LangGraph 构建有向图状态机，每个节点对应一个处理阶段（意图识别、工具调用、结果校验等），边代表状态转移条件。
>
> 选择 LangGraph 而非纯 LangChain 的原因：
>
> 1. **流程可控**：LangChain 的 AgentExecutor 是黑盒循环，难以精确控制每一步；LangGraph 的图结构让每个节点可独立调试和替换。
> 2. **支持条件分支和循环**：比如多轮追问、工具调用失败重试，用图的条件边表达更清晰。
> 3. **状态管理**：LangGraph 内置 State 机制，天然适合多轮对话的上下文传递。
>
> 实际效果：复杂任务的步骤完成率从 LangChain 链式调用的约 70% 提升到了 90% 以上。

------

### Q2：你的 Text2SQL 工作流是怎么设计的？如何保证生成 SQL 的准确性和安全性？

**参考回答：**

> 整体分为 **四步**：
>
> 1. **意图识别与路由**：先用 LLM 判断用户问题是否属于数据查询类，非查询类直接拦截。
> 2. **智能推荐表**：将用户问题与数据库元数据（表名、字段注释）做语义匹配，推荐 Top-K 相关表，缩小 Schema 范围，减少幻觉。
> 3. **SQL 生成**：将推荐表的 DDL + 业务语义说明注入 Prompt，让模型生成 SQL。采用 Few-shot 示例引导格式。
> 4. **安全校验**：用 **SQLGlot** 对生成的 SQL 做 AST 解析，拦截 DDL/DML 操作（DROP、DELETE、UPDATE 等），只允许 SELECT 语句通过；同时做方言转换适配不同数据库。
>
> 准确率方面：在内部测试集上，简单查询准确率约 **92%**，复杂多表 JOIN 约 **85%**。主要通过优化 Schema 描述和增加 Few-shot 示例来迭代提升。

### Q3：你提到用"渐进式披露"三层加载架构解决上下文窗口溢出，具体怎么做的？

**参考回答：**

> 核心思路是 **按需加载，而不是一次性把所有 Prompt 塞进上下文**。
>
> 三层结构：
>
> - **第一层（元信息）**：只加载技能包的名称和一句话描述，占用极少 Token。Agent 根据用户问题判断需要调用哪个技能。
> - **第二层（指令层）**：命中某个技能后，加载该技能的 SKILL.md（核心指令和约束），大约几百 Token。
> - **第三层（参考资料）**：只在需要时加载详细参考文档、示例数据等，用完即释放。
>
> 效果：相比把所有技能 Prompt 一次性注入，**Token 消耗降低约 60%~70%**，同时避免了上下文过长导致的模型注意力稀释和幻觉问题。

### Q4：你的 RAG 系统中，分块策略是怎么设计的？如何处理长文档？

**参考回答：**

> 我们采用 **语义分块 + 滑动窗口重叠** 的策略：
>
> - 先按文档结构（标题、段落）做粗分块
> - 对超长段落，按语义相似度切分，每块控制在 **512~1024 Token**
> - 相邻块之间保留 **10%~15% 的重叠**，防止上下文断裂
>
> 对于长文档（如几百页的报告），额外做了：
>
> - **层级摘要**：先生成章节摘要，检索时先匹配摘要层，再定位到具体段落
> - **元数据增强**：每个 chunk 附加来源文档名、章节标题等元信息，辅助过滤
>
> 这套方案在我们知识库场景中，召回准确率相比固定长度分块提升了约 **15%**。

### Q6：多智能体（A2A）系统中，Agent 之间是怎么通信和协作的？

**参考回答：**

> 我们的多 Agent 架构采用 **编排者模式（Orchestrator Pattern）**：
>
> - 一个 **主 Agent（Orchestrator）** 负责任务分解和调度
> - 多个 **子 Agent** 各自负责特定领域（如数据查询、文档生成、审批流程）
>
> 通信机制：
>
> - 通过 **结构化消息**（JSON Schema）传递任务和结果，而非自由文本
> - 每个子 Agent 有明确的输入/输出契约
> - 主 Agent 维护全局状态，子 Agent 只关注自己的子任务
>
> 为什么不用去中心化的自由协作：在业务场景中，可控性和可追溯性更重要，编排者模式更容易调试和保证一致性。

### Q8：FastAPI 的异步流式输出是怎么实现的？遇到过什么坑？

**参考回答：**

> 核心实现：
>
> ```python
> @app.get("/chat/stream")
> async def chat_stream(query: str):
>     async def generate():
>         async for chunk in llm.astream(query):
>             yield f"data: {chunk}\n\n"
>     return StreamingResponse(generate(), media_type="text/event-stream")
> ```
>
> 遇到的坑：
>
> 1. **Nginx 缓冲问题**：Nginx 默认会缓冲响应，导致流式失效。需要加 `X-Accel-Buffering: no` 头或配置 `proxy_buffering off`。
> 2. **连接超时**：长任务（如复杂 SQL 生成）可能超过网关超时时间，需要设置合理的 timeout 或做心跳保活。
> 3. **异步阻塞**：如果工具调用中有同步 IO（如同步数据库查询），会阻塞事件循环。需要用 `asyncio.to_thread()` 或异步驱动。

### Q11：你提到用 SQLGlot 做 SQL 安全校验，为什么不用正则？SQLGlot 的优势是什么？

**参考回答：**

> 正则的问题：
>
> - 无法处理嵌套子查询、CTE、注释中的关键词等复杂情况
> - 容易被绕过（比如大小写混淆、Unicode 替换）
> - 维护成本高，规则越写越多
>
> SQLGlot 的优势：
>
> 1. **AST 级别解析**：真正把 SQL 解析成语法树，能精确识别语句类型（SELECT/INSERT/DDL）
> 2. **方言支持**：一套代码适配 MySQL、PostgreSQL、Hive 等多种方言
> 3. **可编程遍历**：可以遍历 AST 检查是否包含危险操作（如子查询中的 DELETE）
> 4. **SQL 改写**：可以自动加 LIMIT、加 WHERE 条件等安全措施
>
> 简单说：正则是在字符串层面"猜"，SQLGlot 是在语法层面"懂"。

### Q12：如果模型产生幻觉（比如 Text2SQL 生成了不存在的表名），你怎么处理？

**参考回答：**

> 多层防线：
>
> 1. **Prompt 层**：明确告知模型可用的表名和字段列表，约束生成范围
> 2. **推荐表层**：先做语义匹配推荐相关表，模型只能从推荐列表中选择
> 3. **校验层**：SQLGlot 解析后，检查表名和字段名是否存在于元数据中，不存在则拒绝并让模型重新生成
> 4. **兜底层**：连续 2 次生成无效 SQL，返回友好提示并建议用户换一种问法
>
> 核心原则：**不信任模型的任何输出，所有生成结果都必须经过程序化校验后才能执行。**

### Q1：ReAct 和 CoT 的本质区别是什么？分别适合什么场景？

**参考回答：**

> **CoT（Chain of Thought）**：纯推理链，模型一步步"想"，但不与外部环境交互。适合 **纯逻辑推理** 场景，如数学题、逻辑分析。
>
> **ReAct（Reasoning + Acting）**：在推理的基础上加入 **行动（工具调用）和观察（获取结果）**，形成 Thought → Action → Observation 的循环。适合 **需要获取外部信息** 的场景，如查数据库、调 API。
>
> 本质区别：CoT 是"闭卷考试"，ReAct 是"开卷考试"——可以查资料再作答。
>
> 在我的项目中：
>
> - 意图识别、任务规划阶段用 CoT 让模型先想清楚步骤
> - 工具调用阶段用 ReAct，让模型根据上一步结果动态决定下一步

### Q2：LangGraph 中的 State 是怎么管理的？如何避免状态膨胀？

**参考回答：**

> LangGraph 的 State 本质是一个 **TypedDict 或 Pydantic Model**，定义了整个图运行过程中需要传递的所有字段。每个节点接收当前 State，返回需要更新的字段（增量更新，不是全量覆盖）。
>
> 状态膨胀问题及解决：
>
> 1. **消息列表无限增长**：多轮对话中 messages 越来越长。解决：设置滑动窗口（只保留最近 N 轮）或用摘要压缩历史消息。
> 2. **中间结果堆积**：工具调用的原始返回可能很大。解决：只保留结构化摘要，不存原始响应。
> 3. **多分支状态**：并行节点各自写入状态可能冲突。解决：用 LangGraph 的 `Annotated[list, operator.add]` 做列表合并，或用 reducer 函数自定义合并逻辑。
>
> 核心原则：**State 只存决策需要的信息，不存过程数据。**

### Q3：Agent 的短期记忆和长期记忆你具体是怎么实现的？

**参考回答：**

> **短期记忆（Working Memory）**：
>
> - 就是当前对话的上下文窗口
> - 实现：维护一个 messages 列表，包含 system prompt + 最近 N 轮对话
> - 优化：超过窗口限制时，用 LLM 对早期对话做 **摘要压缩**，替换原始消息
>
> **长期记忆（Long-term Memory）**：
>
> - 基于向量数据库存储历史交互和知识
> - 实现：每轮对话结束后，将关键信息（用户偏好、历史决策等）提取出来，Embedding 后存入向量库
> - 检索时：用当前问题做语义检索，召回相关的历史记忆，注入 Prompt
>
> **分层设计**：
>
> | 层级     | 存储             | 生命周期 | 用途               |
> | :------- | :--------------- | :------- | :----------------- |
> | 工作记忆 | 内存（messages） | 单次会话 | 当前对话上下文     |
> | 会话记忆 | Redis/DB         | 跨轮次   | 用户本次会话的历史 |
> | 长期记忆 | 向量库           | 永久     | 用户画像、历史知识 |
>
> 关键难点：什么时候写入长期记忆、写什么。我们用 LLM 做了一次"记忆提取"，判断哪些信息值得持久化。

### Q4：你提到用 Agent Skills 封装技能包，SKILL.md 的结构是什么样的？和直接写 Prompt 有什么区别？

**参考回答：**

> SKILL.md 的结构大致如下：
>
> ```markdown
> # 技能名称：财务报销审核
> 
> ## 触发条件
> 当用户问题涉及报销流程、报销标准、报销审批时激活
> 
> ## 核心指令
> - 你必须按照以下规则审核报销单...
> - 输出格式为 JSON...
> 
> ## 约束
> - 不得编造报销政策
> - 超出权限范围时转人工
> 
> ## 参考文档

> ```
>
> 和直接写 Prompt 的区别：
>
> | 维度       | 直接写 Prompt              | 技能包封装                 |

> | 可维护性   | 改一个 Prompt 可能影响全局 | 每个技能独立修改，互不影响 |
> | Token 效率 | 所有 Prompt 一次性加载     | 按需加载，节省 60%+ Token  |
> | 可复用性   | 难以跨项目复用             | 技能包可插拔，跨项目迁移   |
> | 可测试性   | 难以单独测试               | 每个技能可独立评测         |
>
> 本质上是把 **Prompt 工程从"手工作坊"升级为"模块化工程"**。

### Q5：AG-UI 协议中的事件类型有哪些？你是怎么处理前端渲染的？

**参考回答：**

> AG-UI 定义的核心事件类型：
>
> - `RUN_STARTED` / `RUN_FINISHED`：Agent 运行的开始和结束
> - `TEXT_MESSAGE_START` / `TEXT_MESSAGE_CONTENT` / `TEXT_MESSAGE_END`：文本流式输出
> - `TOOL_CALL_START` / `TOOL_CALL_ARGS` / `TOOL_CALL_END`：工具调用过程
> - `STATE_SNAPSHOT` / `STATE_DELTA`：Agent 状态快照和增量更新
> - `CUSTOM`：自定义事件（如审批流状态变更）
>
> 前端渲染实现：
>
> - 用 **Vercel AI SDK** 的 `useChat` / `useCompletion` hook 接收事件流
> - 根据事件类型分发到不同 UI 组件：
>   - `TOOL_CALL_START` → 显示"正在调用 XX 工具..."的动画
>   - `TEXT_MESSAGE_CONTENT` → 打字机效果渲染文本
>   - `STATE_DELTA` → 更新侧边栏的状态面板
>
> 关键优化：前端做了 **事件缓冲和批量渲染**（requestAnimationFrame），避免高频事件导致页面卡顿。

### Q6：DPO 和 RLHF 的区别是什么？你为什么选择 DPO？

**参考回答：**

> **RLHF（基于人类反馈的强化学习）**：
>
> - 需要训练一个 **奖励模型（Reward Model）**，再用 PPO 算法优化策略模型
> - 流程：SFT → 训练 RM → PPO 对齐
> - 问题：PPO 训练不稳定、超参敏感、计算资源需求大
>
> **DPO（Direct Preference Optimization）**：
>
> - 跳过奖励模型，直接用 **偏好数据对**（chosen vs rejected）优化策略模型
> - 本质是把 RLHF 的目标函数转化为一个分类问题
> - 优势：训练更稳定、不需要额外的 RM、资源需求小
>
> 选择 DPO 的原因：
>
> 1. 我们团队资源有限，PPO 的工程复杂度太高
> 2. DPO 只需要构造偏好数据对，我们的用户反馈（采纳/拒绝）天然就是偏好信号
> 3. 实测效果：在幻觉率降低方面，DPO 和 RLHF 差距不大，但工程成本低很多

### Q7：LoRA 微调的原理是什么？rank 怎么选？

**参考回答：**

> **原理**：LoRA 的核心思想是 **低秩分解**。不直接修改原始权重矩阵 W，而是在旁边加一个低秩分支：
>
> ```
> W' = W + ΔW = W + B × A
> ```
>
> 其中 A 是 d×r 矩阵，B 是 r×k 矩阵，r 远小于 d 和 k。训练时只更新 A 和 B，原始 W 冻结。
>
> **rank（r）的选择**：
>
> - r 太小（如 4）：表达能力不足，学不到领域知识
> - r 太大（如 128）：接近全量微调，失去参数效率优势，且容易过拟合
> - 经验值：**8~64**，一般从 16 开始试
> - 我们的实践：在领域 SFT 任务上，r=16 效果就足够了；更复杂的任务（如风格迁移）可能需要 r=32~64
>
> **其他关键参数**：
>
> - `alpha`：缩放系数，通常设为 rank 的 2 倍（如 r=16, alpha=32）
> - `target_modules`：一般选 q_proj、v_proj（注意力层的 Q 和 V），效果最好且参数最少

### Q8：你们的知识库支持哪些文档格式？文档解析这块是怎么做的？

**参考回答：**

> 支持的格式：PDF、Word、Markdown、HTML 网页、Excel（部分场景）
>
> 解析方案：
>
> - **PDF**：用 **MinerU**（开源 PDF 解析工具），能较好地处理多栏排版、表格、公式
> - **Word/Markdown**：用 Unstructured 库，按段落和标题结构切分
> - **表格**：单独提取为结构化数据，生成自然语言描述后入库
>
> 遇到的坑：
>
> 1. **扫描件 PDF**：纯图片无法直接解析，需要先过 OCR（PaddleOCR）
> 2. **复杂表格**：合并单元格、跨页表格解析容易出错，我们做了后处理校验
> 3. **页眉页脚**：需要过滤，否则会引入噪声。MinerU 有自动过滤能力，但偶尔误判，需要人工抽检
>
> 核心原则：**解析质量决定了 RAG 的上限**，所以我们在文档解析上投入了大量精力。

### Q9：你们的混合检索具体是怎么实现的？BM25 和向量检索的结果怎么融合？

**参考回答：**

> **两路召回**：
>
> - **BM25**：基于关键词的稀疏检索，擅长精确匹配（如产品编号、专有名词）
> - **向量检索**：基于 Embedding 的稠密检索，擅长语义匹配（如"怎么请假"匹配"休假流程"）
>
> **融合策略**：用 **RRF（Reciprocal Rank Fusion）** 算法：
>
> ```
> RRF_score(d) = Σ 1 / (k + rank_i(d))
> ```
>
> 其中 k 通常取 60，rank_i(d) 是文档 d 在第 i 路检索中的排名。
>
> 为什么用 RRF 而不是简单加权：
>
> - BM25 和向量检索的分数量纲不同，直接加权需要归一化，效果不稳定
> - RRF 只看排名不看分数，天然解决了量纲问题，且对异常值鲁棒
>
> **Rerank**：融合后取 Top-20，用 BGE-Reranker 做精排，最终取 Top-5 送入 LLM。
>
> 效果：混合检索 + Rerank 相比纯向量检索，召回准确率提升约 **12%**。

### Q10：Agent 安全治理中的"可控、可审、可停"具体是怎么实现的？

**参考回答：**

> **可控（Controllable）**：
>
> - 工具调用白名单：Agent 只能调用预注册的工具，不能自主"发明"工具
> - 参数校验：每个工具调用前校验参数合法性（类型、范围、权限）
> - 操作分级：只读操作自动执行，写操作（如提交审批、修改数据）需要人工确认
>
> **可审（Auditable）**：
>
> - 全链路日志：用 Langfuse 记录每一步的输入、输出、决策依据
> - 关键操作审计：涉及数据变更的操作单独记录审计日志，保留操作人、时间、内容
> - 支持回溯：任何一次 Agent 执行都可以完整重放
>
> **可停（Stoppable）**：
>
> - 设置最大执行步数（如 10 步），超过则强制终止
> - 设置 Token 消耗上限，防止死循环
> - 提供人工中断接口，管理员可以实时终止正在运行的 Agent 任务
> - 异常检测：连续 N 次工具调用失败则自动熔断

### Q11：你们的"微调 → 上线 → 埋点反馈 → 再训练"闭环具体是怎么运转的？

**参考回答：**

> 完整闭环分四步：
>
> **① 微调**：基于领域语料做 SFT（LoRA），针对高频场景（如报销审核、数据查询）提升准确率
>
> **② 上线**：新模型灰度发布（先 10% 流量），对比新旧模型的指标
>
> **③ 埋点反馈**：
>
> - 用户行为埋点：是否采纳了 Agent 的回答（点赞/点踩）、是否手动修改了 SQL
> - 系统埋点：工具调用成功率、幻觉检测标记、响应延迟
> - 定期（每周）汇总反馈数据，标注为 chosen / rejected 对
>
> **④ 再训练**：
>
> - 用新的偏好数据做 DPO 训练
> - 在测试集上评估，确认指标提升后进入下一轮灰度
>
> 周期：大约 **2~3 周一个迭代**。初期迭代频率高（每周），稳定后改为双周。
>
> 关键指标：幻觉率从初期的 15% 降到了 5% 以下，SQL 生成准确率从 82% 提升到 93%。

### Q12：Langfuse 和 LangSmith 你都用了，它们的区别是什么？各自适合什么场景？

**参考回答：**

> | 维度     | Langfuse                                       | LangSmith                             |
> | :------- | :--------------------------------------------- | :------------------------------------ |
> | 部署方式 | **可私有化部署**（Docker 自建）                | SaaS 为主（也有私有化但较贵）         |
> | 开源     | ✅ 完全开源                                     | ❌ 闭源                                |
> | 框架绑定 | 框架无关，支持 OpenAI SDK / LangChain / 自定义 | 和 LangChain 生态深度绑定             |
> | 核心功能 | Trace、评测、Prompt 管理、成本分析             | Trace、评测、Dataset 管理、Playground |
> | 适合场景 | 对数据隐私要求高、需要私有化                   | 深度使用 LangChain 生态               |

> - **生产环境用 Langfuse**（私有化部署，数据不出内网）
> - **开发调试阶段用 LangSmith**（和 LangChain/LangGraph 集成更丝滑，Playground 方便调试 Prompt）
>
> 如果只能选一个，我推荐 Langfuse，因为私有化部署在企业场景中几乎是刚需。

### Q13：你们的知识采纳率是怎么定义和计算的？这个指标有什么局限性？

**参考回答：**

> **定义**：用户在收到 Agent 回答后，是否直接使用了该回答（而非重新提问或手动查找）。
>
> **计算方式**：
>
> ```
> 知识采纳率 = 被采纳的回答数 / 总回答数 × 100%
> ```
>
> 采纳的判定：
>
> - 用户点击了"有帮助"按钮（显式反馈）
> - 用户没有追问且没有转人工（隐式反馈，权重较低）
> - 用户在一定时间内没有重复提问相同问题（行为推断）
>
> **局限性**：
>
> 1. **幸存者偏差**：用户可能觉得回答一般但懒得点踩，导致采纳率虚高
> 2. **不区分质量**：用户可能只是"看了一眼"就算采纳，不代表回答真的正确
> 3. **场景差异大**：简单问题的采纳率天然高，复杂问题的采纳率低，混在一起看会失真
>
> **改进措施**：
>
> - 分场景统计（简单查询 vs 复杂分析）
> - 加入人工抽检（每周随机抽 50 条回答做质量评估）
> - 结合"客诉处理时效"等业务指标交叉验证

### Q14：如果让你重新设计这个系统，你会做哪些不同的选择？

**参考回答：**

> 这个问题考察反思能力，可以从以下几个角度回答：
>
> 1. **文档解析更早引入多模态模型**：初期我们用规则 + OCR 解析文档，后来才发现 MinerU 这类工具效果好很多。如果重来，会一开始就做技术调研对比，而不是自己造轮子。
> 2. **评测体系前置**：我们是系统上线后才补的评测体系，导致初期迭代缺乏量化依据。如果重来，会在开发阶段就搭好评测框架。
> 3. **更细粒度的权限控制**：初期的权限设计比较粗（按部门），后来发现同一部门内不同角色的知识范围也不同，返工了一次。
> 4. **考虑端侧部署**：部分高频简单查询其实可以用小模型在端侧处理，减少大模型调用成本。
>
> > 💡 回答这类问题的关键：展示你的 **反思能力和全局视野**，而不是否定过去的工作。
